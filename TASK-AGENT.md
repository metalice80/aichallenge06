# День 6. Первый AI-агент

## 1. Цель

С нуля разработать небольшое web-приложение на **Kotlin + Spring Boot**, реализующее простого AI-агента.

Агент должен:

- принимать сообщения пользователя;
- отправлять запросы в OpenAI через API;
- получать ответы LLM;
- поддерживать диалог с учетом предыдущих сообщений;
- отображать ответы в web-интерфейсе;
- показывать статистику использования токенов и времени ответа;
- позволять пользователю полностью сбросить текущий диалог.

Главное архитектурное требование: **Agent должен быть отдельной сущностью приложения**, инкапсулирующей логику взаимодействия с LLM.

Это не должен быть просто HTTP-вызов OpenAI из Controller.


# 6. Agent

Создать отдельную abstraction для агента.

Например:

```kotlin
interface Agent {

    fun sendMessage(message: String): AgentResponse

    fun reset()
}
```

Конкретная реализация может называться:

```text
ChatAgent
```

или:

```text
OpenAiAgent
```

Agent должен отвечать за:

- получение сообщения пользователя;
- валидацию сообщения;
- добавление system prompt;
- управление текущим Conversation;
- формирование контекста для LLM;
- передачу запроса в `LlmClient`;
- получение результата;
- добавление ответа модели в Conversation;
- формирование `AgentResponse`;
- сброс текущего диалога.

Agent **не должен самостоятельно выполнять HTTP-запросы**.

---

# 7. LLM Client

Техническое взаимодействие с OpenAI вынести в отдельный компонент.

Предусмотреть abstraction примерно следующего вида:

```kotlin
interface LlmClient {

    fun chat(request: LlmRequest): LlmResponse
}
```

Реализация:

```text
OpenAiClient
```

`OpenAiClient` отвечает за:

- формирование HTTP-запроса к OpenAI;
- authentication;
- serialization;
- deserialization;
- обработку HTTP status;
- извлечение ответа модели;
- извлечение token usage;
- преобразование OpenAI-specific DTO во внутреннюю модель.

`OpenAiClient` не должен:

- управлять историей разговора;
- решать, какие сообщения должны находиться в контексте;
- содержать бизнес-логику Agent;
- зависеть от web UI.

---

# 8. Модели LLM

Не передавать OpenAI-specific DTO по всему приложению.

Предусмотреть внутренние модели.

Например:

```kotlin
data class LlmRequest(
    val messages: List<ChatMessage>
)
```

и:

```kotlin
data class LlmResponse(
    val content: String,
    val model: String,
    val inputTokens: Int?,
    val outputTokens: Int?,
    val totalTokens: Int?
)
```

Конкретные поля могут немного отличаться, если этого требует выбранный OpenAI API.

---

# 9. Conversation

Историю диалога представить отдельной моделью `Conversation`.

Например:

```kotlin
class Conversation {

    private val messages: MutableList<ChatMessage>

    fun add(message: ChatMessage)

    fun messages(): List<ChatMessage>

    fun clear()
}
```

Не обязательно использовать именно такой API, но история не должна быть случайным `MutableList` внутри Controller.

Модель сообщения:

```kotlin
data class ChatMessage(
    val role: Role,
    val content: String
)
```

Роли:

```kotlin
enum class Role {
    SYSTEM,
    USER,
    ASSISTANT
}
```

---

# 10. Multi-turn conversation

Агент должен поддерживать настоящий последовательный диалог.

Например, пользователь пишет:

```text
User:
Что такое JVM?
```

Agent получает ответ:

```text
Assistant:
JVM — это виртуальная машина Java...
```

Затем пользователь спрашивает:

```text
User:
А зачем она нужна?
```

Второй запрос к LLM должен содержать предыдущий контекст:

```text
SYSTEM:
Ты полезный AI-ассистент...

USER:
Что такое JVM?

ASSISTANT:
JVM — это виртуальная машина Java...

USER:
А зачем она нужна?
```

Таким образом модель должна понимать контекст разговора.

---

# 11. System prompt

Agent должен иметь system prompt.

Использовать примерно следующую инструкцию:

```text
Ты полезный AI-ассистент.
Отвечай понятно, точно и по существу.
Учитывай предыдущие сообщения пользователя в текущем диалоге.
```

System prompt не должен быть размазан по исходному коду.

Вынести его в:

- конфигурацию;

или

- отдельную константу/configuration component.

Архитектура должна позволять легко изменить system prompt.

---

# 12. Состояние чата

Для текущей учебной версии допустимо считать, что приложение обслуживает:

```text
один пользователь → один активный Conversation
```

Использование базы данных не требуется.

Историю можно хранить в памяти приложения.

При этом код желательно спроектировать так, чтобы в будущем можно было перейти к:

```text
conversationId → Conversation
```

и поддерживать несколько независимых чатов.

Реализовывать `conversationId` сейчас не требуется.

# 13. OpenAI Configuration

API key запрещено хранить в исходном коде.

Использовать environment variable:

```text
OPENAI_API_KEY
```

Конфигурация приложения должна быть примерно такой:

```yaml
openai:
  api-key: ${OPENAI_API_KEY}
  model: <model>
  system-prompt: >
    Ты полезный AI-ассистент.
    Отвечай понятно, точно и по существу.
```

Модель должна задаваться через конфигурацию.

Не хардкодить название модели внутри Agent или OpenAiClient.

Если выбранная модель недоступна для аккаунта или используемого endpoint, модель должна легко заменяться через configuration без изменения исходного кода.

После получения ответа:

- добавить ответ в чат;
- обновить статистику;
- снова разрешить ввод.

# 16. Статистика

После каждого успешного обращения к OpenAI отображать статистику **последнего LLM-запроса**.

Минимально показать:

```text
Model
Response time
Input tokens
Output tokens
Total tokens
```

Backend должен возвращать эти данные вместе с ответом агента.

Например:

```kotlin
data class AgentResponse(
    val content: String,
    val model: String,
    val inputTokens: Int?,
    val outputTokens: Int?,
    val totalTokens: Int?,
    val responseTimeMs: Long
)
```

Если выбранный OpenAI endpoint использует другие названия token usage, преобразовать их во внутреннюю модель приложения.

Если какое-либо значение usage отсутствует в API-ответе, приложение не должно падать.

# 17. Измерение времени

Время ответа измерять на backend.

Измерять непосредственно продолжительность реального вызова LLM:

```text
Agent
  ↓
start timer
  ↓
OpenAiClient.chat(...)
  ↓
OpenAI API
  ↓
response
  ↓
stop timer
```

Не включать в это время:

- rendering страницы;
- frontend processing;
- пользовательские действия.

Хранить значение в миллисекундах:

```text
responseTimeMs
```

Frontend может отображать его в секундах.

# 19. Сброс чата

На странице должна быть кнопка:

```text
Сбросить чат
```

При нажатии:

```text
Browser
   ↓
POST /api/chat/reset
   ↓
Controller
   ↓
Agent.reset()
   ↓
Conversation.clear()
```

После успешного ответа frontend должен:

- удалить отображаемую историю сообщений;
- очистить статистику последнего запроса;
- оставить пустое поле для нового сообщения.

Следующий запрос должен начинать новый независимый разговор.

Предыдущая история не должна передаваться OpenAI.

System prompt при следующем запросе должен применяться снова.

---

# 20. Controller

Controller должен быть максимально тонким.

Он отвечает только за:

- HTTP;
- validation входного DTO;
- вызов Agent;
- преобразование результата в response.

Недопустимо:

```text
ChatController
       ↓
   OpenAI API
```

Обязательно:

```text
ChatController
       ↓
     Agent
       ↓
  OpenAiClient
       ↓
   OpenAI API
```

Controller не должен знать:

- OpenAI URL;
- API key;
- OpenAI request JSON;
- system prompt;
- правила формирования истории;
- детали взаимодействия с OpenAI API.

---

# 21. Обработка ошибок

Корректно обработать минимум следующие ситуации:

- пустое сообщение;
- отсутствует `OPENAI_API_KEY`;
- OpenAI вернул `401 Unauthorized`;
- OpenAI вернул `429 Too Many Requests`;
- OpenAI вернул `5xx`;
- timeout;
- network error;
- некорректный OpenAI response.

Stack trace не должен отображаться пользователю.

Frontend должен получить понятное сообщение, например:

```text
Не удалось получить ответ от модели.
Попробуйте ещё раз.
```

Backend должен логировать технические детали ошибки.

API key никогда не должен попадать:

- в response;
- в frontend;
- в browser JavaScript;
- в логи.

---

# 22. История при ошибке

Если пользовательское сообщение было добавлено во внутреннюю историю, но запрос OpenAI завершился ошибкой, Conversation не должен оставаться в неконсистентном состоянии.

После ошибки история должна позволять пользователю корректно повторить запрос.

Выбрать простое и предсказуемое поведение и покрыть его тестом.


- system prompt передан в LLM;
