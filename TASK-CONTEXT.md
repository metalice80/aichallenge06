# День 7. Сохранение контекста агента

## Цель

Доработать существующий AI Agent на Kotlin + Spring Boot так, чтобы история диалога сохранялась между перезапусками приложения.

Сейчас история чата хранится только в памяти процесса.

После остановки приложения она теряется.

Необходимо реализовать persistent storage для Conversation.

После перезапуска приложения агент должен восстановить предыдущую историю и продолжить диалог так, как будто приложение не выключалось.

---

# 1. Требуемое поведение

Сценарий должен работать следующим образом:

```text
Запуск приложения
       ↓
Пользователь:
Меня зовут Алексей.
       ↓
Agent:
Приятно познакомиться, Алексей.
       ↓
Пользователь:
Я изучаю Kotlin.
       ↓
Agent:
...
       ↓
Остановка приложения
       ↓
Повторный запуск приложения
       ↓
Пользователь:
Как меня зовут и что я изучаю?
       ↓
Agent:
Вас зовут Алексей, и вы изучаете Kotlin.
```

История предыдущих сообщений должна быть восстановлена из persistent storage и передана LLM вместе с новым сообщением.

---

# 2. Хранилище

Использовать SQLite.

История сообщений не должна храниться только в памяти.

SQLite database file должен находиться локально в проекте или в configurable location.

Например:

```text
./data/agent.db
```

Директорию:

```text
data/
```

добавить в `.gitignore`.

---

# 3. Архитектура

Существующую архитектуру:

```text
Controller
    ↓
Agent
    ↓
Conversation
    ↓
LlmClient
    ↓
OpenAI
```

доработать до:

```text
Controller
    ↓
Agent
    ↓
Conversation
    ↓
ConversationRepository
    ↓
SQLite
```

При этом взаимодействие с LLM остаётся:

```text
Agent
    ↓
LlmClient
    ↓
OpenAI API
```

Общая схема:

```text
                     ┌──────────────────┐
                     │   ChatController │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │      Agent       │
                     └───────┬──────────┘
                             │
                ┌────────────┴─────────────┐
                │                          │
                ▼                          ▼
      ┌──────────────────┐      ┌──────────────────┐
      │   Conversation   │      │    LlmClient     │
      └────────┬─────────┘      └────────┬─────────┘
               │                         │
               ▼                         ▼
      ┌──────────────────┐          OpenAI API
      │ConversationRepo  │
      └────────┬─────────┘
               │
               ▼
             SQLite
```

# 4. ConversationRepository

Добавить отдельную abstraction для persistence.

Например:

```kotlin
interface ConversationRepository {

    fun load(): Conversation

    fun save(conversation: Conversation)

    fun clear()
}
```

Допускается другой интерфейс, если он лучше соответствует архитектуре.

Важно:

Agent не должен напрямую работать с SQLite.

Agent должен работать через repository.

---

# 5. Хранение сообщений

Каждое сообщение должно сохраняться как отдельная запись.

Минимально сохранять:

```text
id
role
content
createdAt
```

Пример структуры таблицы:

```sql
CREATE TABLE chat_message (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

Допускается другая схема, если она остаётся простой и понятной.

---

# 6. Role

Существующую модель ролей сохранить:

```kotlin
enum class Role {
    SYSTEM,
    USER,
    ASSISTANT
}
```

В persistent storage сохранять значение роли в текстовом виде.

Например:

```text
SYSTEM
USER
ASSISTANT
```

---

# 7. Восстановление контекста при запуске

При старте приложения необходимо загрузить сохранённые сообщения из SQLite.

Алгоритм:

```text
Application start
      ↓
ConversationRepository.load()
      ↓
получить сохранённые сообщения
      ↓
создать Conversation
      ↓
передать его Agent
```

Если база данных пустая:

```text
Conversation = empty
```

System prompt при этом должен добавляться по существующей логике приложения.

Не создавать дубликаты system message при каждом перезапуске.

---

# 8. Сохранение сообщений

После успешного сообщения пользователя и успешного ответа LLM необходимо сохранить обновлённую Conversation.

Минимальный сценарий:

```text
User message
      ↓
Agent
      ↓
LLM request
      ↓
LLM response
      ↓
Conversation обновлена
      ↓
ConversationRepository.save(...)
```

После успешного ответа persisted state должен содержать:

```text
USER
ASSISTANT
```

соответствующие текущему обмену.

---

# 9. Поведение при ошибке LLM

Если OpenAI вернул ошибку, состояние persistent storage не должно становиться неконсистентным.

Например:

```text
USER message
      ↓
OpenAI error
```

После ошибки не должно оставаться незавершённого пользовательского сообщения, если текущая логика приложения предполагает атомарный обмен.

Выбрать одно из двух предсказуемых поведений:

1. сохранять только полностью завершённые пары USER + ASSISTANT;

или

2. сохранять USER отдельно, но тогда повторный запрос должен корректно обрабатывать незавершённое состояние.

Для учебного проекта предпочтителен первый вариант:

```text
успешный exchange → сохраняем
ошибка → persistent state не меняем
```

# 10. Reset чата

Существующая кнопка:

```text
Сбросить чат
```

теперь должна очищать:

```text
in-memory Conversation
+
persistent SQLite storage
```

Алгоритм:

```text
POST /api/chat/reset
      ↓
Agent.reset()
      ↓
Conversation.clear()
      ↓
ConversationRepository.clear()
```

После reset:

- UI очищается;
- память очищается;
- SQLite история очищается;
- после перезапуска приложения старый чат не должен возвращаться.

# 11. UI после перезапуска

После повторного запуска приложения желательно восстановить историю и в web UI.

Для этого добавить endpoint:

```http
GET /api/chat/history
```

Пример response:

```json
[
  {
    "role": "USER",
    "content": "Меня зовут Алексей"
  },
  {
    "role": "ASSISTANT",
    "content": "Приятно познакомиться, Алексей."
  }
]
```

При открытии страницы frontend должен:

```text
GET /api/chat/history
```

и отрисовать ранее сохранённые сообщения.

System message в UI не показывать.

# 12. Persistence implementation

Для SQLite можно использовать:

- Spring Data JDBC;
- Spring Data JPA;
- JdbcTemplate.

Предпочтение отдать самому простому варианту.

Не усложнять проект лишней ORM-архитектурой.

Для этой задачи хорошо подходит:

```text
Spring JDBC / JdbcTemplate + SQLite
```

или эквивалентное простое решение.

---

# 13. Конфигурация SQLite

Путь к базе должен задаваться через configuration.

Например:

```yaml
storage:
  database-path: ${AGENT_DB_PATH:./data/agent.db}
```

Не хардкодить абсолютный путь.

---

# 14. Инициализация схемы

При первом запуске приложение должно само создать необходимую таблицу, если её ещё нет.

Не требовать ручного запуска SQL.

Допустимо использовать:

```text
schema.sql
```

или programmatic initialization.

---

# 15. Требования к Agent

Agent по-прежнему должен оставаться отдельной сущностью.

Не переносить persistence logic в Controller.

Правильно:

```text
Controller
   ↓
Agent
   ↓
ConversationRepository
```

Неправильно:

```text
Controller
   ↓
SQLite
```

Controller не должен знать:

- где хранится история;
- как устроена таблица;
- как работает SQLite;
- как Conversation сериализуется или сохраняется.

# 21. Критерии готовности

Задача считается выполненной, если:

- история хранится в SQLite;
- история не теряется после остановки приложения;
- после запуска Conversation восстанавливается;
- новый запрос учитывает предыдущие сообщения;
- UI показывает восстановленную историю;
- reset очищает и память, и SQLite;
- после reset и рестарта старая история не возвращается;
- Agent не зависит напрямую от SQLite;
- Controller не работает напрямую с persistence;
- unit-тесты проходят;
- integration test repository проходит;
- проект успешно собирается.
